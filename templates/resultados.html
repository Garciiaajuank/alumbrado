Productos, resultados y conclusiones

Comparación entre los productos esperados y los alcanzados, evidencias verificables del funcionamiento, conclusiones por objetivo, limitaciones, oportunidades de mejora y fuentes consultadas del proyecto Alumbrado Público Inteligente.

PLANIFICACIÓN

Productos esperados

Entregables planteados al inicio del módulo para responder a la necesidad de medir el consumo y detectar fallas en el alumbrado público.

  • • Maqueta funcional: prototipo con una placa ESP32-S3, un reloj y LED que simulan postes encendidos entre las 18:00 y las 06:00.
  • • Modelo relacional: base de datos en SQL Server con usuarios, procesos, dispositivos, mediciones y eventos.
  • • Simulación de un millón de mediciones: datos de una red de 100 postes, con errores controlados para limpiar.
  • • ETL y Data Warehouse: paquete SSIS que limpia y carga un modelo estrella.
  • • Dashboard y sitio web: reporte de Power BI integrado en una página publicada, con cinco conocimientos y dos decisiones.

Cumplimiento de los objetivos

Objetivo general: construir una plataforma de datos que integre las mediciones del alumbrado público, las limpie con un ETL y las almacene en un data warehouse para analizar consumo, fallas y eventos.

Objetivo específico Estado Resultado
Diseñar un modelo relacional con usuarios, procesos, dispositivos, mediciones y eventos ✓ Cumplido Nueve tablas con claves primarias y foráneas. La relación entre usuarios y procesos se resuelve con una tabla puente.
Simular al menos 1.000.000 de mediciones con errores controlados ✓ Cumplido 1.050.000 mediciones con nulos, el valor 9999 y estados escritos de varias formas. El script se puede repetir.
Diseñar un data warehouse con modelo estrella y granularidad definida ✓ Cumplido Una fila de hechos es una medición válida de un poste en un momento de 5 minutos. Hay cuatro dimensiones: poste, fecha, hora y estado.
Implementar un ETL en SSIS que limpie, homologue y cargue sin duplicados ✓ Cumplido 1.043.772 filas cargadas y 6.228 rechazadas (0,59 %). Al repetir la carga no se duplicó ningún dato.
Responder preguntas de negocio con consultas analíticas y un dashboard ✓ Cumplido El dashboard y las consultas SQL dan las mismas cifras. De ellos salen cinco conocimientos y dos decisiones.

Conclusiones

Lo que aprendimos, lo que mostró el análisis y lo que no se puede afirmar con datos simulados.

Lo que aprendimos

Los datos casi nunca llegan limpios: en la simulación el estado de un poste venía escrito de siete formas distintas, y sin homologarlo los análisis habrían salido mal. También vimos que las dimensiones se cargan antes que los hechos, porque la tabla de hechos necesita sus claves, y que guardar los rechazos con su motivo permite comprobar que no se perdió nada.

Lo que mostró el análisis

El consumo se reparte casi por igual entre las cinco zonas (0,07 % de diferencia) y ocurre solo en las 12 horas nocturnas, a 3,94 kWh por hora y por día. El poste P030 encabeza las fallas con 42, aunque ese valor también puede salir por azar, y la tasa de falla de la red es de 0,52 %.

Decisiones que salen del análisis

La primera es revisar los diez postes con más fallas, empezando por P030. La segunda es probar bajar la intensidad de las luminarias entre las 00:00 y las 05:59 en una zona de prueba, porque la madrugada concentra el 50,7 % del consumo. Las dos son acciones de verificación, no de causa demostrada.

Aporte del proyecto

Muestra cómo una red de alumbrado, aunque sea simulada, se puede medir y analizar con datos para ver dónde se gasta la energía y qué postes revisar primero, en línea con los ODS 7 (energía asequible y no contaminante) y 11 (ciudades y comunidades sostenibles).

Dashboard integrado y funcionando

El reporte de Power BI está integrado en la sección Dashboard de esta página y se puede usar desde ella: se cambia de página del reporte, se aplican filtros y las gráficas responden al hacer clic. No requiere iniciar sesión. Las cifras que muestra coinciden con las consultas SQL sobre el Data Warehouse (1.727,10 kWh, 2.705 fallas y 1.043.772 lecturas válidas).

Limitaciones

  • Datos simulados. Las mediciones siguen reglas que definimos y no vienen de una red real. Los conocimientos muestran el método y deben validarse con datos reales.
  • Prototipo pequeño. Solo 6 de los 100 postes existen físicamente en la maqueta.
  • Fallas asignadas al azar. El ranking de postes con más fallas refleja variación aleatoria y no señala postes defectuosos.
  • Período corto. Son 37 días, con 5 o 6 observaciones por día de la semana, así que no se pueden evaluar patrones semanales ni estacionales.
  • Voltaje y potencia con rangos fijos. No reflejan las variaciones de una red eléctrica real.
  • Datos en vivo sin historial. Lo que envía el ESP32 se muestra en tiempo real, pero no se guarda en la base de datos.
  • Dependencia de la red. La maqueta necesita una red WiFi con internet para enviar su estado.
  • Servidor gratuito. Si nadie visita la página por un rato, Render la suspende y el primer acceso puede tardar cerca de un minuto.

Oportunidades de mejora

  • ETL incremental y programado. Guardar el último medicion_id cargado y ejecutar el paquete de forma automática.
  • Historial en vivo. Guardar en la base de datos lo que envía el ESP32 para que el dashboard se actualice solo.
  • Más sensores en la maqueta. Un sensor de luz para el encendido real y uno de corriente para medir el consumo de cada poste.
  • Alertas automáticas por correo o mensaje ante fallas, sobreconsumo o bajo voltaje.
  • Reporte con control de acceso. Publicar el reporte de Power BI en un espacio de trabajo con usuarios, en lugar de la opción pública, y con actualización programada.
  • Datos reales. Probar el análisis con mediciones de una red de alumbrado real.
